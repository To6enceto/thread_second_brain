# Feature: Desktop project portability

**From build-plan:** feature 61
**Build attempt:** 1
**Branch:** feature/desktop-project-portability
**Status:** verified

## Goal

Let the independent desktop window create the same portable project packages as the plugin, compare a selected checkpoint with current permitted content and import a package as reviewed new copies with durable recovery, using the shared package format and the desktop's current read permissions. Never overwrite existing files or widen read access.

## In scope

- Export: choose permitted project files and eligible consented PDFs from the shared export inventory, preview the exact package (manifest, entries, omissions and limitations), recheck scope and current snapshots, and create a new `.thread-project.json` file inside the current read roots and outside exclusions. Refuse existing names, case/Unicode collisions and changed sources. The checkpoint is a selected project package, not a full backup.
- Package selection for comparison and import: one `.thread-project.json` file chosen explicitly through the native file dialog, read once as an inert bounded snapshot and validated with the shared decoder before any content is shown. No vault enumeration outside read roots; no arbitrary renderer path.
- Comparison: read-only comparison of a validated package with the current permitted project using the shared comparator (unchanged, changed, missing, current-only, limits and omissions). No restoration, note changes, model calls or grants.
- Import: preview a new top-level destination folder outside every read root, exclusion and PDF grant; list destinations, identity warnings and collisions; apply as create-only new copies with a durable desktop import journal, readback hash verification and recovery for interrupted imports (continue with adopted verified copies or close recovery leaving partial files). Imported folders stay outside read grants until explicitly granted.
- Native accessible controls, finite main-owned IPC, cancellation, keyboard/light/dark and stale/denied/empty/error states.

## Out of scope

Destructive restore, overwrite or merge modes; ID rewriting; importing plugin import history or settings; packages larger than the shared limits; network transfer; packaging/distribution (62); changes to the shared package format or plugin behavior.

## Build loop

Continuous Mode builds these steps serially with self-review and Verify after each. Step checkpoint commits are disabled. Actual Electron acceptance with authored synthetic vaults and an actual plugin/desktop package round trip, plus a fresh passing independent review, are required before archive and local merge. At most two repairs per failing check/finding; never weaken gates. Preserve all previous evidence and archives.

## Data / contracts

Keep `thread-project` schema version 1 and PACKAGE_LIMITS: 100 entries, 2 MiB text, 16 MiB per PDF, 32 MiB expanded, 48 MiB serialized, 1024-character paths; at most 10 PDF originals and 32 MiB per export. The desktop import journal reuses the shared `ImportState` schema (at most 100 receipts, one pending) in a separate desktop profile file; it never reads or writes plugin `project-imports.json`. Imports and exports require desktop writer ownership.

Export destinations are new files inside current read roots and outside exclusions (stricter than the plugin's non-excluded rule so desktop writes stay in visible scope). Import roots are new top-level folders outside all read roots, exclusions and PDF grants, as the shared import contract requires; the import writer may create folders/files only inside that root and only read back files it created for verification. Package snapshots come only from the native dialog and are inert data until decoded. Comparison and export reads use current permissions and PDF consent; package content never grants reads.
